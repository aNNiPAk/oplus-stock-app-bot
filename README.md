# OPlus Stock App Bot — multi-donor

Автоматические каналы APK для Obtainium. Источник выбирается из свежих OTA разных **OPPO, OnePlus и realme**, а не из прошивки одного телефона.

## Выбор источников и версии

`config/donors.json` задаёт pool моделей, регионы, квоты производителей и разделы. По умолчанию проверяются до шести OTA ветки 16: до двух от каждого производителя. OnePlus в каталоге может называться `OP 15`; это имя нормализуется перед фильтрацией. Повторные глобальные регионы одного устройства исключаются, китайская ветка считается отдельным источником.

Свежесть OTA используется для выбора ограниченного числа доноров. Победитель среди извлечённых APK определяется по настоящему Android `versionCode`, а не по номеру или дате прошивки. Это поиск среди выбранных доноров, не гарантия максимальной версии во всех существующих прошивках.

## Языки и релизы

- **Stable:** базовый APK содержит русский (`ru`).
- **Experimental:** русского нет, но есть английский (`en`), либо язык ресурсов не указан.
- **Rejected:** языки указаны явно, но нет ни русского, ни английского.

Stable публикуется обычным релизом. Более новый experimental публикуется prerelease с `-exp` в tag и не заменяет Latest. RRO overlays проверяются как диагностика; их русский язык не делает базовый APK русским автоматически.

APK публикуется без изменений. Подпись проверяется через `apksigner`; SHA-256 сертификата записывается, но **совпадение с предыдущим сертификатом не требуется**. Это учитывает установленное пользователем разрешение на обновления с другой подписью.

В отчёт входят языки APK, связанные overlays, `uses-library`, native `.so`, SHA-256 и точный источник OTA. Наличие этих данных не означает, что приложение проверено на конкретном телефоне.

## GitHub Actions

Каждый канал вызывает `.github/workflows/update-stock-app.yml` с именем пакета. Его собственный `GITHUB_TOKEN` публикует APK в этом же репозитории; PAT не требуется.

Job сначала выполняет настоящий dry-run. Если публикация включена, повторно проверяет выбранные APK и загружает их из staging того же job без повторного извлечения OTA. Версии опубликованных релизов перечитываются перед публикацией.

Для ручной проверки: канал → Actions → Update OPlus … → Run workflow → `dry_run: true`. Для публикации отключите `dry_run`. Daily schedule включён в каждом канале. В центральном bot-репозитории проверка всегда выполняется без публикации.

`Inspect multi-donor pool` показывает выбранные источники без извлечения. `Validate multi-donor OTA extraction` проверяет полный проход календаря по шести донорам.

## Извлечение

HTTP Range извлекает только нужный раздел, не весь многогигабайтный ZIP. Сохранены исправления для подписанных CDN URL, размера HTTP Range и 64-битных offsets больших payload. Разделы очищаются после просмотра, чтобы они не накапливались на диске runner. Нестандартный формат сертификатов с ротацией ключа тоже поддерживается.

`oplus_release_bot.py` и `dump_payload.py` остаются проверенными транспортными инструментами. Автоматический multi-donor выбор использует `oplus_multi_donor.py`, а не model из legacy `config.json`.

## Модуль совместимости из архива

`OPlusCompat` в архиве — необязательный prototype с пустым набором overrides. Он не содержит готовых патчей регионов или зависимостей. Бот сохраняет диагностику для последующего разбора конкретных проблем.

### Экономия чтения OTA

HTTP Range читается блоками по 4 MiB с ограниченным кешем 32 MiB: соседние операции payload используют один запрос. Проверки диапазонов, размера архива и хешей сохраняются. Overlays проверяются только в уже извлечённых разделах; отдельные разделы ради диагностики не скачиваются. Поэтому список overlays может быть неполным. В логах указаны число запросов, объём чтения и время каждого донора.

Каналы пока выполняют независимые проходы по OTA; общего кеша между репозиториями нет.
